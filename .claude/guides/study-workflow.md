# 책/문서 학습 정리 워크플로우

**적용 시점**: 책, 논문, 외부 문서를 읽으며 학습 내용을 정리할 때 (Luna DX11, Real-Time Rendering 등 모든 외부 학습 자료)

---

## 핵심 원칙

### 0. 책 근거 원칙 (최우선)

**노션·Concepts 어디든, 정리에 들어가는 모든 내용은 반드시 그 책(또는 해당 자료)에서의 근거가 있어야 한다.**

- 책에 명시되지 않은 내용을 "당연히 알 거니까", "일반적으로 그러니까" 식으로 추가하지 않는다
- 추측·일반 상식·다른 자료에서 가져온 내용으로 빈 곳을 메우지 않는다
- 책에 없는 내용을 보강하고 싶으면 **출처를 명시한 별도 섹션**으로 분리하거나, 별도 Concepts 문서로 빼서 그 자료의 출처를 명확히 한다
- 정리하면서 "이 부분 책에서 본 적 있던가?" 의심이 들면 그 페이지로 돌아가 확인 후 인용

**보강·정정이 필요한 경우 처리 방법** (정확한 근거가 있을 때):
- 책 본문 정리는 **그대로 유지**한다 (책이 이렇게 말했다는 사실 자체를 보존)
- 그 **바로 아래에** 별도 블록으로 보강·정정 내용을 추가한다
- 보강 블록에는 **근거 출처를 명시** — 같은 책의 다른 절(예: "§1.1.1 참고"), 다른 책, 표준 문서 등
- **두 가지 형식 사용 구분**:
    - **짧은 한 줄/한 단락 보강**: blockquote(`>`) 사용
        ```
        > **참고/보강 (근거: §1.1.1)**: 책 §1.1.3은 차원만 언급했지만,
        > 실제로는 같은 frame의 좌표여야 한다.
        ```
    - **여러 항목 종합/요약 정리**: 별도 헤딩 섹션 사용 (`###` 또는 `####`)
        ```
        ### §1.3 종합 (보강, 근거: §1.3 전체)
        ... 여러 항목, 긴 설명 ...
        ```
    - **별도 섹션 안에 여러 주제가 있으면 하위 헤딩(`####`)으로 구분**
        ```
        ### §1.3.1 보강: ... (근거: 일반 그래픽스 지식)
        #### 책의 설명 한계
        ...
        #### 흔한 시나리오
        ...
        #### 핵심 메커니즘
        ...
        ```
- 이렇게 하면 "책이 말한 것"과 "보강된 이해"를 구분 가능 → 나중에 다시 읽을 때 출처 추적 용이

**Why:** 학습 정리의 신뢰성. 나중에 다시 읽었을 때 "이게 진짜 책 내용인지, 내 해석인지, 다른 데서 본 건지" 헷갈리지 않게 하기 위함. Concepts 문서로 추출할 때도 출처가 명확해야 다른 자료와 교차 검증이 가능하다.

**How to apply:** 매 섹션 정리 시 책의 해당 부분(페이지/절 번호)을 옆에 두고 작성. 노션 정리 끝에 책 페이지/절 표기 권장. 추출 시 책에 직접 나온 표현·정의·공식·코드만 사용.

### 1. 분리 원칙

학습 자료를 정리할 때는 **저작권 리스크 회피 + 학습 효과 + 엔진 코드 연결**을 모두 챙기기 위해 정리 위치를 분리한다.

| 위치 | 공개/비공개 | 용도 | 작성 자유도 |
|------|------------|------|------------|
| **노션** | 비공개 | 챕터별 학습 노트 (책 흐름 그대로) | 인용·예제·필기 자유 |
| **Git 리포 `Docs/Concepts/`** | 공개 | 일반 개념 문서 (책 의존 없이 본인 언어 재구성) | `documentation.md` 규칙 준수 |
| **Git 이슈** | 공개 | 학습 중 떠오른 엔진 구현 아이디어 | `workflow.md`의 연구/학습 이슈 패턴 |

**왜 분리하는가**:
- 공개 Git 리포에 책 문장·예제·그림을 그대로 옮기면 저작권 침해 소지 (paraphrase여도 책 구조 그대로 따라가는 displacive summary는 위험)
- 비공개 노션에서는 자유롭게 정리 → 학습 효과 극대화
- 일반 그래픽스/수학 지식으로 재구성 가능한 부분만 공개 리포에 → 다른 개발자에게도 도움

## 절차

**정리 단위는 책의 목차를 그대로 따른다.** 책이 Part → Chapter → Section → Subsection으로 구성되어 있으면 그 계층을 그대로 노션·Concepts 문서에 반영한다.

- 헤딩 레벨도 책의 목차 계층을 그대로 매핑 (예: 책의 `1.3 The Dot Product` → 노션 `### 1.3 The Dot Product`)
- 챕터·절 번호와 제목을 책의 표기 그대로 유지 (영문판이면 영문 그대로, 한글판이면 한글 그대로)

### 진행 흐름 (2단계 구조)

**A. 노션 정리 단계 — 절(Section) 단위로 반복**

한 장(Chapter)이 끝날 때까지 아래를 반복:

1. **본문 추출** — Claude가 다음 절 분량을 추출해서 사용자에게 보여줌 (PDF는 `pdftotext` 사용)
2. **노션 자동 입력 (비공개)** — Claude가 노션 MCP로 해당 절을 비공개 페이지에 작성. 인용·예제·필기 자유롭게 포함. 사용자가 직접 쓰겠다고 하면 즉시 중단.
3. **질문 단계** — 사용자 질문 → Claude 답변 → 필요 시 보강 블록 추가 (책 근거 원칙 준수)

→ 절을 다 끝내면 다음 절로. 한 장이 끝날 때까지 반복.

**B. Concepts 추출 단계 — 한 장 끝났을 때 1회**

장(Chapter) 단위 노션 정리가 끝났을 때만 진행:

4. **Concepts 추출 후보 제안** — Claude가 그 장 전체에서 `Docs/Concepts/` 하위에 일반 개념 문서로 추출할 가치 있는 항목을 제안
    - 추출 기준: 책 의존 없이 일반 그래픽스/수학/엔진 지식으로 재구성 가능
    - 책 특유의 예제·연습문제는 제외
    - 후보가 빈약하면 **스킵하고 다음 장으로**. 관련 주제는 누적해서 나중에 묶어 추출 가능
5. **각 후보를 별도 GitHub 이슈로 발행** (⚠️ 사용자 컨펌 필수)
    - 한 대화에서 모든 후보 문서를 다 작성하면 컨텍스트가 너무 길어짐 → **이슈로 분리해 별도 세션에서 처리**
    - 이슈 제목 예: `docs(Concepts): 회전·자세 표현과 정규직교화 전략 정리`
    - 이슈 본문에는: 후보 개요 / 연관 보강 노트 링크 / 책 출처 (Luna 1장 등) / 작성 기준 (`documentation.md` 규칙)
    - 일부 후보가 `.claude/guides/workflow.md`의 **연구/학습 이슈 패턴 (전략 비교 + 체감 실험 자매 쌍)**에 해당하면 그 패턴 적용 — 자매 이슈도 같이 발행
6. **문서 초안 작성 + 티키타카** — **이슈 단위로 별도 작업 세션에서** 진행. 사용자가 작업 시작할 때 그 이슈를 가져오면 Claude가 노션 보강 + 책 정리 참고해서 `Docs/Concepts/<주제>/<문서>.md` 초안 작성. `.claude/guides/documentation.md` 규칙 준수. 출처는 하단 "참고문헌" 섹션에 명시.
7. **PR 생성** — `.claude/guides/workflow.md`에 따라 브랜치 (`docs/이슈번호`) → 커밋 → PR → 사용자 최종 리뷰
8. **머지** — 사용자가 머지

**왜 2단계로 분리하는가**: Concepts 추출은 한 장 전체의 맥락이 있어야 "어느 주제를 묶어 빼낼지" 판단이 잘 된다. 절 단위로 매번 평가하면 빈약하거나 단편적인 후보만 나와 비효율.

**왜 이슈로 분리하는가**: 한 대화에서 4~5개 Concepts 문서를 다 작성하면 토큰·컨텍스트가 폭발. 이슈로 분리하면 각 문서 작업이 독립 세션이 되어 집중 가능. 우선순위에 따라 순서·스킵도 자유.

## 부속 규칙

### 구현 아이디어
학습 중 "엔진에 구현해보고 싶다"는 아이디어가 나오면 별도 이슈로 발행.
- ⚠️ **이슈 생성 전 사용자 컨펌 필수**
- `.claude/guides/workflow.md`의 연구/학습 이슈 패턴 (전략 비교 + 체감 실험 자매 쌍) 활용

### 수식 표현

- 노션 정리에서 **수학 공식은 TeX(KaTeX)로 작성**한다
- **모든 수식은 `$$...$$`로 감싼다** (single `$...$`는 노션에서 렌더링 안 됨)
    - 노션은 `$$...$$`를 단독 줄이면 block으로, 본문 안에 끼워넣으면 inline으로 자동 처리
- ⚠️ **`$$` 와 LaTeX 사이에 공백을 두면 안 된다 (특히 여는 쪽)** — 공백이 있으면 노션이 빈 inline equation 두 개로 파싱하고 가운데 LaTeX 가 평문으로 떨어짐 (`\frac` → `frac`)
    - 잘못: `$$ y(t)=-\frac{1}{2}gt^2 $$` ❌ (양옆 공백)
    - 잘못: `$$y(t)=-\frac{1}{2}gt^2 $$` ❌ (닫는 쪽 공백)
    - 올바름: `$$y(t)=-\frac{1}{2}gt^2$$` ✓ (양옆 공백 없음)
- ⚠️ **`$$...$$` 바깥쪽**(앞·뒤)에는 **반드시 공백을 둔다** — 한글 조사·괄호·쉼표·마침표 등 어떤 글자가 붙어도 escape되어 평문화될 수 있음
    - 잘못: `$$\theta$$는 각이다` ❌ (닫는 `$$` 뒤에 한글 조사)
    - 잘못: `($$n$$이 단위 벡터일 때)` ❌ (괄호·조사 모두 붙음)
    - 잘못: `$$u$$, $$v$$ 사이 각` ❌ (쉼표 붙음)
    - 올바름: `$$\theta$$ 는 각이다` ✓ (바깥쪽 공백)
    - 올바름: `( $$n$$ 이 단위 벡터일 때)` ✓
    - 올바름: `$$u$$ , $$v$$ 사이 각` ✓
- **규칙 정리**: 수식의 **안쪽**(`$$` 와 LaTeX 사이)은 절대 공백 금지, **바깥쪽**(`$$` 와 한글/특수문자 사이)은 항상 공백 필수
- block(단독 줄)은 위아래 빈 줄로 분리하면 가장 안전. 단독 줄 block 의 경우에도 `$$` 와 LaTeX 는 한 줄씩 분리 (각자 단독 줄)
- 책의 식 번호(eq. 1.1 등)는 그대로 보존하되, 식 자체는 TeX 렌더링되도록 작성
- 단순 좌표 튜플 `(x, y, z)` 같이 텍스트로 충분한 것은 굳이 TeX로 안 써도 됨
- Concepts 문서(GitHub Markdown)도 동일 규칙

### 그림·도표 처리

- 기본은 텍스트로만 정리한다. 모든 그림을 노션에 옮기려 하지 않는다 (PDF 원본이 사용자 손에 있으므로).
- 정리 중 "이건 그림이 진짜 필요하다" 싶은 지점에만 본문에 마킹을 남긴다.
- 마킹 형식: `📷 [Figure X.X — 간단한 묘사 (책 약 p.YY)]`
    - 예: `📷 [Figure 1.5 — left/right-handed 좌표계 비교 (책 약 p.35)]`
    - 페이지 번호는 책의 인쇄된 페이지 번호 사용 (PDF 뷰어 페이지가 아님)
- 사용자가 PDF에서 직접 캡쳐해서 마킹 자리에 붙여넣음 (비공개 노션이므로 학습용 사용 OK)
- **이미지를 붙여넣은 후에도 마킹은 이미지 바로 아래에 캡션으로 남겨둔다** — 어느 그림이 어느 페이지에서 왔는지 추적 가능. 나중에 다시 볼 때 출처가 명확해짐.
- **외부 이미지는 가져오지 않는다** — 책 그림과 미묘하게 다를 수 있어 본문 설명과 어긋날 위험. 책 근거 원칙과도 충돌.
- 그림이 거의 필수인 영역: 좌표계 손방향, 외적 오른손 법칙, 변환 시각화, 파이프라인 다이어그램, 조명 기하 등
- 그림 없이도 충분한 영역: 단순 정의, 코드 위주, 수식이 본질인 부분 (행렬 대수 등)

### 저작권 가드레일
- 공개 Git 리포에는 책 문장·예제·그림을 그대로 옮기지 않는다
- paraphrase도 책 구조를 그대로 따라가는 displacive summary는 피한다
- Concepts 문서 하단에 "참고문헌" 섹션으로 출처 명시 (Luna 외 다른 자료도 같이)
- 책 그림 대신 직접 그린 다이어그램 사용

- 자동 목차는 페이지 상단 (출처 바로 아래)
- 장 목록은 그 다음 — 챕터 페이지 mention들만 모아둠
- 참고 문서는 장 목록 바로 아래 — **장별로 `##` 헤딩으로 그룹화**해서 보강·종합 페이지 mention 모음
- 콘텐츠 DB는 페이지 맨 아래 — 전체 페이지 통합 뷰
- 진행 상황·책 소개 등은 별도 섹션으로 두지 않음 (필요 시 출처 인용문 안에 한 줄로)

**책 페이지 안에 인라인 DB 한 개 두기 (장 + 보강 페이지 컨테이너)**:
- DB 이름 예: `콘텐츠` 또는 책에 맞춰 `Luna DX11 콘텐츠`
- 속성:
  - `이름` (title) — 페이지 제목
  - `종류` (select): `Chapter` / `보강` / `종합` 등
  - `식별자` (text): `Ch.1`, `§1.3.1 보강`, `§1.3 종합` 등
- 한 책의 모든 챕터 페이지 + 보강 페이지가 이 DB 안에 항목으로 존재
- DB는 페이지 본문에 인라인으로 임베드 (사용자가 종류별로 필터링/그룹화 view를 수동 설정)

**유지보수**:
- 새 챕터 정리 시: `# 장 목록`에 mention 추가, `# 참고 문서`에 `## Chapter N` 섹션 추가
- 새 보강 페이지 생성 시: 해당 챕터 섹션의 mention 목록에 추가
- DB는 새 페이지가 자동 추가되므로 별도 작업 불필요

**Chapter 페이지 구조**:
- 제목: `Chapter X 제목` (예: `Chapter 1 Vector Algebra`)
- 종류: `Chapter`
- 본문: 책의 절(section) 단위 정리. 보강은 `<mention-page>`로 해당 보강 페이지 참조

**보강 페이지 구조**:
- 제목: `§X.Y 보강: 주제` (예: `§1.3.1 보강: orthonormal이 깨지는 상황`)
- 종류: `보강`
- 본문: 책 근거 명시 + 보강 내용 (앞서 정한 보강 형식 규칙 준수)

**왜 분리하는가**:
- 책 한 권의 정리가 한 페이지에 누적되면 페이지가 너무 커져 로딩·검색·편집이 불편
- 챕터별 / 보강 주제별 페이지로 나누면 개별 단위로 관리·재참조 용이
- 보강 글은 다른 챕터에서도 참조될 수 있어 별도 페이지가 자연스러움

**인용/이미지**: 비공개이므로 책 그림·캡처·코드 자유롭게 포함 가능
